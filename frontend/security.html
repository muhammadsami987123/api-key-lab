Security model

Last updated: March 2026

Short version: your key is used for one request, forwarded to the provider you chose, and forgotten. It is not written to a database, a log file or a cache.

Where your key goes

  • In your browser: the key is held in sessionStorage for the tab you are using. Closing the tab deletes it. There is no cookie and no localStorage copy.
  • In transit: it is posted over HTTPS to our serverless function at /api/verify or /api/chat.
  • At the provider: the function adds the key as an auth header and calls the one provider endpoint that answers your request.
  • Afterwards: the function returns the provider’s response and exits. Nothing is persisted.

Ollama and other local endpoints are the exception: those requests go straight from your browser to your machine and never reach our servers.

What we deliberately do not do

  • No database, queue, object storage or cache for request data.
  • No console.log of headers, bodies or keys. Error handling returns messages to the caller directly.
  • No analytics, session recording, fingerprinting or advertising pixels.
  • No third-party key validation services. Your key is only sent to the provider you selected.
  • We do not probe other providers with your key to "guess" which one it belongs to. Ambiguous prefixes are surfaced to you instead.

Hardening on the proxy

  • Same-origin only: requests from other websites are rejected.
  • Body size capped at 256 KB and request timeouts at 20 seconds.
  • Per-IP rate limiting (40 checks/min, 60 chat calls/min) so the endpoint cannot be used as a bulk relay.
  • Outbound calls are restricted to the selected provider. Custom base URLs must be HTTPS and cannot target private or loopback addresses, which blocks server-side request forgery.
  • Cache-Control: no-store on every API response.
  • Strict Content-Security-Policy, X-Content-Type-Options: nosniff, no framing and no inline scripts.

Verify it yourself

  1. Open DevTools → Network, run a check, and read the request payload.
  2. Close the tab, reopen the site — the key field is empty.
  3. Try an invalid key: the report shows the provider’s own error, not a generic one.

Residual risk, stated honestly

Any tool that accepts a secret in a web form carries risk. Use a scoped, low-limit key when testing, rotate it afterwards if you are unsure, and never paste production billing keys into any third-party page. Platform providers (Vercel) may retain standard infrastructure metadata such as IP and request path for their own operational logs; request bodies and keys are not part of that metadata.
